## 3. 核心规则与交互约定

### 3.1 棋盘和阻挡

1. 棋盘由有限的二维网格组成，每格为空或包含一个箭头，不允许重叠。
2. 每个箭头固定朝上、下、左、右之一。基础版不允许玩家旋转箭头或改变其所在格子。
3. 检测从箭头前方相邻格开始，一直检查到棋盘边界；不检测箭头自身所在格。
4. 路径内只要存在其他箭头，就视为被阻挡；阻挡箭头的朝向不影响判断。
5. 位于身后、其他行或其他列的箭头不构成阻挡。路径允许跨过任意数量的空格，不能只检测相邻格。
6. 位于边界且朝向棋盘外的箭头可以直接飞出，不访问数组范围之外的位置。
7. 箭头消除后，其格子变为空格，后续检测使用当前棋盘状态。

### 3.2 成功点选

**前置条件**：处于游戏状态，没有正在播放的棋盘动作，且鼠标左键点中了仍存在的箭头所在格。

- 无阻挡时，该箭头沿朝向直线飞出棋盘。
- **实现约定**：动画播放期间保留逻辑棋盘中的箭头；当箭头图形整体离开棋盘区域时，原子地删除箭头、更新剩余数量并结束本次动作。
- 本次动作不消耗失误机会。剩余箭头数量为零时，在动画结束后进入通关状态。
- 飞出动画建议持续 200—400 毫秒，可根据距离调整；数值为可调的表现参数。

### 3.3 被阻挡点选

- 箭头不得消除、换格或挤动其他箭头。
- **实现约定**：立即将剩余失误次数减 1，同时播放约 200—300 毫秒的短暂变色或晃动，并提示“前方有箭头阻挡”。
- 动画中的位移只是视觉效果，结束后箭头回到原始绘制位置，逻辑坐标始终不变。
- 若扣减后仍有机会，反馈结束后继续游戏；若降至零，反馈结束后显示失败结果。
- 一次有效点击只扣除一次，剩余次数不得为负。

### 3.4 失误、重开与无效输入

以下均为**实现约定**：

| 行为 | 约定 |
| --- | --- |
| 初始失误次数 | 每关默认 3 次，作为关卡配置保存 |
| 进入下一关 | 使用下一关的初始布局和完整失误次数，不继承上一关的剩余次数 |
| 点击空格、棋盘外区域、已消除箭头的位置 | 无状态变化，不扣次数 |
| 鼠标右键、拖动或长按 | 不触发连续点选；只处理左键按下事件 |
| 飞出或碰撞反馈期间继续点选棋盘 | 忽略，不排队，不重复消除或扣次数 |
| 游戏中点击重新开始 | 立即重置当前关卡的布局、计数和提示，无须回到第一关 |
| 动画期间重新开始 | 取消动作和延迟处理，再重置；旧动作不能继续修改新一局 |
| 结果界面点击棋盘 | 不处理，必须使用结果界面的按钮 |
| 关闭窗口 | 在所有状态下均能正常退出，包括动画期间 |

## 4. 界面需求

### 4.1 开始界面

显示游戏名称、简短规则和“开始游戏”按钮。规则至少说明：按箭头方向判断路径、无阻挡可消除、被阻挡会消耗失误机会、清空全部箭头即可通关。

**实现约定**：“开始游戏”进入第 1 关。基础版不持久化进度，每次启动从开始界面进入。

### 4.2 游戏界面

必须显示：

- 当前关卡，例如“第 1 / 3 关”。
- 网格棋盘及方向清晰的箭头。
- 剩余箭头数量。
- 剩余失误次数。
- “重新开始”按钮。

布局应保证文字清楚、按钮和棋盘不重叠。成功飞出和碰撞必须有可辨认的视觉反馈，不能仅依赖控制台输出。方向通过箭头形状表达，不只使用颜色区分。

**实现约定**：采用固定大小桌面窗口，建议 960 × 720；棋盘居中，状态区位于上方，操作区位于下方。不同大小的棋盘自动计算格子尺寸，整格作为点击区域。窗口具体尺寸可以按实际显示效果调整。

### 4.3 结果界面

结果可以使用独立页面或覆盖层，但应明确展示结果并阻止底层棋盘继续接收点选。

| 结果 | 展示内容 | 按钮及行为（实现约定） |
| --- | --- | --- |
| 非最后一关通关 | “第 N 关通关” | “下一关”：初始化下一关；“重玩本关”：重新初始化当前关 |
| 失败 | “挑战失败，失误机会已用尽” | “重新开始”：恢复当前关卡 |
| 最后一关通关 | “全部关卡已通关” | “从第一关重玩”：初始化第 1 关；“返回首页”：显示开始界面 |

最后一关不能继续访问不存在的下一关数据，也不应未经提示自动循环到第一关。非最后一关采用按钮进入下一关，确保玩家可以看清通关结果。

## 5. 状态与流程

建议使用以下状态，名称可按代码习惯调整：

| 状态 | 含义 | 允许的主要操作 |
| --- | --- | --- |
| `START` | 开始界面 | 开始游戏、退出 |
| `PLAYING` | 当前关卡进行中，无动画 | 点击箭头、重新开始、退出 |
| `ANIMATING` | 成功飞出或碰撞反馈中 | 重新开始、退出；忽略棋盘点选 |
| `LEVEL_CLEARED` | 非最后一关已清空 | 下一关、重玩本关、退出 |
| `FAILED` | 当前关卡失误次数耗尽 | 重新开始、退出 |
| `ALL_CLEARED` | 最后一关已清空 | 从第一关重玩、返回首页、退出 |

主要转移关系：

```text
START --开始游戏--> PLAYING
PLAYING --点中箭头--> ANIMATING
ANIMATING --成功飞出且仍有箭头--> PLAYING
ANIMATING --成功飞出且清空非末关--> LEVEL_CLEARED
ANIMATING --成功飞出且清空末关--> ALL_CLEARED
ANIMATING --碰撞且还有失误机会--> PLAYING
ANIMATING --碰撞且失误次数为零--> FAILED
LEVEL_CLEARED --下一关--> PLAYING（下一关初始状态）
PLAYING / ANIMATING / FAILED / LEVEL_CLEARED --重开或重玩本关--> PLAYING（本关初始状态）
ALL_CLEARED --从第一关重玩--> PLAYING（第 1 关初始状态）
ALL_CLEARED --返回首页--> START
```

实现时必须维持以下不变量：

- `remaining_arrows` 与逻辑棋盘实际占用格数一致；建议直接从棋盘计算，避免重复维护。
- 失误次数始终在 `0..max_mistakes` 范围内。
- 同一时刻最多存在一个棋盘动作。
- 关卡模板不被游戏过程修改，加载和重开均创建独立的运行时副本。
- 最后一个箭头只触发一次通关；失败后不再处理新的棋盘动作。

## 6. 数据模型与核心算法

### 6.1 坐标和数据结构

以下为建议采用的**实现约定**：

- 坐标使用从零开始的 `(row, col)`，原点位于棋盘左上角；行向下递增，列向右递增。
- 方向使用 `U`、`D`、`L`、`R`，空格使用 `.`。渲染时绘制对应箭头，不向玩家显示编码字母。
- 关卡可存为 Python 常量中的等长字符串列表；运行时转换为可修改的二维列表。

| 对象 | 字段 | 说明 |
| --- | --- | --- |
| 关卡模板 `Level` | `id`, `name`, `rows`, `max_mistakes` | `rows` 为不可变布局，宽高由布局推导 |
| 运行状态 `Game` | `level_index`, `board`, `mistakes_left`, `state`, `active_action` | 保存当前关卡和动作；不另存容易失步的剩余箭头计数 |
| 动作 `Action` | `kind`, `row`, `col`, `direction`, `elapsed`, `duration` | `kind` 为飞出或碰撞；绘制偏移不写入棋盘 |

加载时检查：棋盘非空、各行等宽、字符合法、至少一个箭头、失误次数为正整数、关卡编号不重复。基础版采用内置固定关卡，无须引入数据库或外部关卡编辑器。

### 6.2 路径检测

| 方向 | 行列增量 `(dr, dc)` |
| --- | --- |
| `U` | `(-1, 0)` |
| `D` | `(1, 0)` |
| `L` | `(0, -1)` |
| `R` | `(0, 1)` |

核心逻辑应与图形库解耦，便于测试。对于有效箭头坐标，可采用以下伪代码：

```text
can_exit(board, row, col):
    (dr, dc) = 该箭头的方向增量
    (r, c) = (row + dr, col + dc)
    while 0 <= r < height and 0 <= c < width:
        if board[r][c] 不是空格:
            return false
        (r, c) = (r + dr, c + dc)
    return true
```

输入是否在棋盘内、是否存在箭头，由调用入口先验证。检查必须先于数组读取，尤其防止 Python 负索引将上边界或左边界误读为另一侧的格子。一次检测的时间复杂度为 `O(max(height, width))`，无需为本作业引入复杂空间索引。

### 6.3 鼠标映射

先判断鼠标是否位于棋盘矩形内，再按格子边长计算行列：`col = floor((x - board_x) / cell_size)`，`row = floor((y - board_y) / cell_size)`。

棋盘采用左、上边界包含，右、下边界不包含的矩形约定；格子边界使用相同规则，避免同一次点击命中两个格子。界面按钮优先处理，不能将重开点击继续传给棋盘。

## 7. 关卡设计与可解性

### 7.1 设计要求

**作业要求**：至少 3 个可正常通关的关卡，每关由提交者实际试玩。

**实现约定**：首版采用以下 3 个原创固定布局，每关均包含四种方向，默认 3 次失误机会。通过棋盘尺寸、箭头数量和阻挡关系增加观察量；难度是否合理还需实际试玩评估。

以下示例已使用独立的逐格路径检查脚本验证列出的消除顺序能够清空棋盘。该验证仅证明布局可解，不代表游戏实现已经通过测试，也不能替代本人实际试玩。

### 7.2 第 1 关：认识阻挡

4 × 4，8 个箭头；初始可直接消除 3 个箭头，适合认识边界和顺序依赖。

```text
. . R D
U . . D
. R . D
L . . R
```

一组通关顺序（零基坐标）：

```text
(1,0) → (3,0) → (3,3) → (2,3) → (1,3) → (0,3) → (0,2) → (2,1)
```

首次点击 `(0,2)` 应发生碰撞；先清除右侧阻挡链后，该箭头才能飞出。

### 7.3 第 2 关：交叉观察

5 × 5，12 个箭头；初始可直接消除 3 个箭头，包含隔着空格的阻挡和跨行列的消除依赖。

```text
. . L L D
R . U . .
U . . U .
U . . R R
. . U . R
```

一组通关顺序：

```text
(0,2) → (0,3) → (1,2) → (1,0) → (2,0) → (2,3)
→ (3,0) → (3,4) → (3,3) → (4,2) → (4,4) → (0,4)
```

### 7.4 第 3 关：连续解锁

6 × 6，20 个箭头；初始可直接消除 4 个箭头，需要连续解除多组阻挡。

```text
L D . L R .
. . . R . R
. D L . L .
U . . . . U
D L L L . .
L L U L L .
```

一组通关顺序：

```text
(0,0) → (0,4) → (1,5) → (1,3) → (3,0) → (3,5) → (5,0)
→ (4,0) → (4,1) → (4,2) → (4,3) → (5,1) → (2,1) → (0,1)
→ (0,3) → (2,2) → (2,4) → (5,2) → (5,3) → (5,4)
```

### 7.5 开发阶段验证

对每个关卡复制棋盘，重复寻找一个当前可飞出的箭头并删除：清空即验证通过；若还有箭头却找不到可飞出的箭头，则布局不可解。

在基础规则下，删除箭头只会减少阻挡，不会产生新阻挡，因此任意合法消除都不会破坏可解性。这使得上述贪心检查足够验证固定关卡，无须穷举所有点击排列。检查过程不得修改原始模板。

关卡数据调整后，应重新验证解序并更新记录；交付前仍须在实际 GUI 中逐关完成一次通关和重开检查。

## 8. 实现方案与运行质量

以下为建议采用的**实现约定**，不限制原文允许的其他 Python 图形库：

- 使用 Python + Pygame，采用本地单进程事件循环。
- 箭头、网格和按钮使用基本图形绘制；中文字体应有可靠的加载方式。若随仓库分发字体，需确认许可并记录来源。
- 动画根据经过时间更新，不能通过阻塞休眠冻结事件处理；目标刷新率为 60 FPS，实际表现需在开发机验证，不预先声称已达到。
- 通过脚本所在目录定位资源，避免依赖启动时的工作目录。
- README 写明实际验证的操作系统、Python 版本和依赖版本；不将未经验证的平台写为已支持。
- 合理拆分规则、关卡和界面，保持单次作业规模，不要求框架、插件系统或复杂继承结构。
